## Pengukuran: halaman terburuk sebelum optimasi

Lihat tabel lengkap di [`docs/performa.md`](performa.md). Dua halaman memiliki angka tertinggi sebelum optimasi, sama-sama **26 query**:

1. Detail mata kuliah dosen.
2. Detail tugas dosen.

Jadi tidak tepat menyebut hanya satu yang paling buruk berdasarkan angka tersebut. Kedua halaman berbagi posisi terburuk. Alasannya, halaman detail merender beberapa bagian sekaligus: informasi utama, daftar/relasi course atau tugas, submission/peserta, serta komponen tampilan. Jika sebuah relasi diakses dari view berulang kali tanpa eager loading, tiap baris dapat menambah query. Sebelum optimasi, query unread notification juga berpotensi diulang melalui composer view yang cakupannya terlalu luas. Perbedaan jumlah data dapat memperbesar biaya, sehingga query count kecil pada fixture satu record saja tidak cukup untuk membuktikan bebas N+1.

Setelah optimasi, detail mata kuliah dosen menjadi **10 query** dan detail tugas menjadi **9 query** dalam fixture pengukuran yang sama. Angka ini mengukur statement, bukan latency.

## Bagaimana N+1 terjadi dan bagaimana mendemokannya

### Penjelasan konsep

Misalnya satu halaman mengambil `N` nilai. Query awal mengambil daftar nilai. Jika setiap nilai lalu mengakses submission, mahasiswa, dan tugas tanpa relasi dimuat di awal, ORM dapat menjalankan query relasi lagi untuk setiap baris. Bentuk sederhananya:

```text
1 query mengambil N nilai
+ query submission/mahasiswa/tugas yang berulang untuk setiap nilai
≈ 1 + (jumlah relasi yang diminta × N)
```

Angka persis tidak selalu sama: relasi yang benar-benar diakses, relasi yang sudah dimuat, dan strategi ORM memengaruhi jumlahnya. Untuk menghindarinya, rekap dosen menggunakan `Grade::with(['submission.student', 'submission.assignment'])`; rekap mahasiswa menggunakan `Grade::with(['submission.assignment.course'])`.

### Hasil yang benar-benar diuji

- Dengan 20 nilai dan eager loading, request rekap course menjalankan **7 query**.
- `Model::preventLazyLoading()` aktif di test. Tes rendering daftar dengan banyak data juga lolos tanpa `LazyLoadingViolationException`.
- Composer unread count dibatasi ke `layouts.app`, supaya tidak menghitung ulang unread count untuk setiap component/subview.
- Dependency `barryvdh/laravel-debugbar` tidak ditemukan di `composer.json`. Karena itu laporan ini **tidak** mengklaim sudah membuka Debugbar atau melihat lonjakan di panel Debugbar.

### Reproduksi visual dengan Debugbar (hanya lokal)

Untuk demonstrasi saat presentasi, gunakan branch/working copy lokal dan jangan lakukan ini di server production:

1. Bila dosen mensyaratkan tampilan Debugbar, pasang sebagai dependency development lokal saja: `composer require --dev barryvdh/laravel-debugbar`.
2. Pastikan Debugbar hanya aktif di local; jangan mengaktifkannya di production karena dapat membocorkan query, parameter, atau informasi request.
3. Siapkan banyak nilai (misalnya 20) untuk satu halaman rekap dan buka tab **Queries** di Debugbar.
4. Catat query count saat kode memakai `with()` seperti semula.
5. Pada working copy lokal, hilangkan sementara eager loading pada query rekap, lalu muat ulang halaman dengan jumlah record yang sama. Jika guard lazy loading tetap aktif, Laravel dapat melempar `LazyLoadingViolationException` sebelum Debugbar menampilkan seluruh pola N+1. Itu juga bukti bahwa ada relasi yang dimuat terlambat.
6. Untuk melihat pertumbuhan query sampai selesai, lakukan percobaan dalam test/lingkungan lokal terisolasi dengan lazy-loading guard dimatikan **sementara hanya untuk percobaan itu**, lalu bandingkan 1 record dengan 20 record. Jangan mengubah guard untuk production. Perkirakan query bertambah seiring baris; ukur angka aktual, jangan menganggap setiap relasi selalu menghasilkan jumlah query yang sama.
7. Pulihkan eager loading dan guard, hapus/rollback perubahan eksperimen, lalu jalankan lagi `php artisan test --filter=PerformanceBudgetTest`.

Alternatif tanpa Debugbar adalah instrumentasi yang sudah dipakai test: `DB::listen()` menghitung SQL selama request. Ini menjadi bukti otomatis, namun bukan bukti screenshot Debugbar. Perbandingan “sebelum” di tabel performa berasal dari baseline yang dicatat test dan diukur dengan fixture yang sama; bukan hasil Debugbar.

## `withCount('students')` dibanding `count($course->students)`

`withCount('students')` meminta Eloquent menambahkan agregasi jumlah mahasiswa sebagai kolom hitungan pada query course. Database mengembalikan angka; model mahasiswa tidak perlu diambil satu per satu. Pada dashboard dosen, `withCount(['students', 'assignments'])` menghasilkan `students_count` dan `assignments_count`.

Sedangkan `$course->students` adalah akses properti relasi. Jika relasi belum dimuat, Eloquent mengambil koleksi mahasiswa dari database dan menghidrasi semua model ke memory; `count($course->students)` baru menghitung koleksi tersebut di PHP. Jika dilakukan dalam loop course, dapat terjadi query per course (N+1) ditambah biaya transfer dan pembuatan objek yang tidak diperlukan hanya untuk mendapatkan angka.

Perbedaan penting: `count($course->students)` bukan hal yang sama dengan `$course->students()->count()`. Bentuk kedua meminta database melakukan `COUNT(*)` dan tidak harus mengambil semua model, tetapi tetap dapat membuat satu query hitung per course jika dipanggil di dalam loop. `withCount()` lebih cocok bila daftar course memang perlu menampilkan hitungan untuk banyak course dalam satu request.

## Index dan bukti `EXPLAIN`

Migrasi [`2026_11_03_000000_add_performance_indexes.php`](../database/migrations/2026_11_03_000000_add_performance_indexes.php) menambahkan:

| Index | Query yang dirancang untuk dibantu |
|---|---|
| `assignments_course_status_due_index` pada `(course_id, status, due_at)` | Penyaringan tugas berdasarkan course/status, lalu batas/urutan `due_at`. |
| `submissions_user_assignment_index` pada `(user_id, assignment_id)` | Lookup submission yang dibatasi pemilik dan tugas. |
| `grades_graded_at_id_index` pada `(graded_at, id)` | Pengurutan rekap nilai terbaru dengan tie-breaker `id`. |

Test menjalankan `EXPLAIN QUERY PLAN` SQLite untuk query yang mewakili tugas terbit mendatang:

```sql
EXPLAIN QUERY PLAN
SELECT *
FROM assignments
WHERE course_id = ? AND status = ? AND due_at >= ?
ORDER BY due_at ASC;
```

Output aktual dari test:

```text
SEARCH assignments USING INDEX assignments_course_status_due_index
(course_id=? AND status=? AND due_at>?)
```

Ini membuktikan query planner **SQLite pada database test** memilih index tersebut untuk query itu. Tes dapat diulang dengan:

```powershell
php artisan test --filter=PerformanceBudgetTest
```

Batas bukti harus dipahami: `php artisan migrate:status` pada database lokal aplikasi menunjukkan migrasi `2026_11_03_000000_add_performance_indexes` **Pending**. Test di atas memakai SQLite in-memory yang menjalankan migrasi otomatis, jadi tidak mengubah database lokal persisten dan tidak membuktikan index telah dibuat di database lokal/production. Sebelum presentasi menggunakan database aplikasi, terapkan migrasi pada lingkungan yang benar:

```powershell
php artisan migrate --force
php artisan migrate:status
```

Untuk MySQL staging/production, jalankan `EXPLAIN` terhadap SQL yang setara dan periksa kolom `key` pada hasilnya, misalnya:

```sql
EXPLAIN
SELECT *
FROM assignments
WHERE course_id = 123 AND status = 'published'
  AND due_at >= CURRENT_TIMESTAMP
ORDER BY due_at ASC;
```

Ganti `123` dengan ID course yang memiliki data realistis. Nama index pada kolom `key` menunjukkan index yang dipilih. Hasil SQLite tidak menjamin MySQL memilih index yang sama: ukuran tabel, distribusi nilai, statistik, versi database, dan bentuk SQL berpengaruh. Index juga mempercepat sebagian read dengan biaya storage dan tambahan kerja saat insert/update/delete; karena itu jangan menambah index tanpa query/use case yang jelas.

## Pagination: mengapa tidak mengambil semua baris

Pagination membatasi jumlah model yang diambil dan dirender pada satu request, mengurangi memory, transfer data, waktu render, dan risiko halaman membesar tanpa batas. Daftar standar menggunakan 15 item; panel dashboard/detail menggunakan batas yang lebih kecil sesuai kebutuhan. Tes membuat lebih dari satu halaman lalu memastikan link halaman berikutnya muncul.

Dashboard tugas mendatang mahasiswa hanya mengambil lima tugas terdekat (`take(5)`). Itu widget ringkas dengan batas eksplisit, bukan daftar lengkap yang diam-diam memuat seluruh tabel. Jumlah pengguna/course di statistik dashboard dihitung dengan agregasi `count()` tanpa memuat semua baris.

Pagination bukan obat untuk semua query: query tetap perlu authorization, filter, eager loading, dan index yang sesuai. Untuk tabel sangat besar, keyset/cursor pagination dapat lebih stabil daripada offset pagination, tetapi mengubah urutan UX dan navigasi; pekerjaan ini mempertahankan paginator yang sudah sesuai dengan halaman aplikasi.

## Cache dashboard, invalidasi, dan data yang tidak boleh stale

`DashboardCache::remember()` membuat key berversi dengan TTL maksimum lima menit. Observer pada `User`, `Course`, `Assignment`, `Submission`, dan `Grade` menaikkan versi cache setelah model disimpan, dihapus, atau dipulihkan. Perubahan enrollment di pivot menginvalidasi secara eksplisit di `EnrollmentController`. Key versi baru membuat request berikutnya membangun cache ulang; entri lama tertinggal sampai TTL habis.

Bagian yang dicache:

- Statistik dashboard admin.
- Daftar course dan hitungan submission belum dinilai di dashboard dosen.
- Daftar course dashboard mahasiswa.

Data yang sengaja tidak dicache antara lain **rekap nilai**. Nilai perlu segera mencerminkan koreksi dosen dan aksesnya bergantung pada course/pengguna yang berwenang. Menampilkan nilai lama atau cache yang tertukar antar pengguna adalah risiko integritas dan privasi. Notifikasi/unread count juga tidak dicache agar aksi tandai dibaca segera terlihat; tugas mendatang tidak dicache karena deadline/status berubah seiring waktu. Daftar/detail materi dan tugas menggunakan pagination/eager loading sebagai gantinya.

Invalidasi berbasis event perlu diperhatikan: operasi bulk seperti `Model::where(...)->update(...)` biasanya tidak mengirim event `saved` untuk setiap model. Jika perubahan semacam itu memengaruhi dashboard cache, kode harus memanggil invalidasi secara eksplisit atau memakai strategi invalidasi lain. TTL lima menit adalah pembatas dampak, bukan pengganti invalidasi yang benar.

## `env()` dan `config:cache`

Konvensi Laravel: panggil `env()` hanya dari file `config/`. Kode aplikasi membaca `config('...')`. Saat `php artisan config:cache` dijalankan, Laravel menggabungkan konfigurasi ke cache. Pada request berikutnya `.env` tidak dimuat seperti mode biasa; `env()` yang dipanggil langsung dari controller/model bisa menghasilkan `null` (kecuali nilai itu memang tersedia sebagai environment variable proses). Karena itu pemanggilan `env()` di luar config dapat bekerja saat development lalu gagal setelah deployment mengaktifkan config cache.

Perubahan `.env` setelah konfigurasi dicache tidak otomatis mengubah konfigurasi aktif. Langkah deployment umumnya: perbarui environment, bangun ulang config cache (`php artisan config:clear` lalu `php artisan config:cache`), dan restart worker/layanan berumur panjang sesuai prosedur deployment. Jangan jalankan `config:cache` dengan nilai environment yang salah. Audit source PHP pada pekerjaan ini menemukan `env()` hanya di `config/`; gunakan `config()` untuk nilai runtime aplikasi.

## Tanya-jawab utama untuk persiapan dosen

### 1. Buka `docs/performa.md`. Halaman mana yang terburuk sebelum optimisasi? Kenapa?

**Jawaban:** Detail mata kuliah dosen dan detail tugas dosen seri terburuk dengan masing-masing 26 query. Keduanya menampilkan banyak bagian dan relasi. Relasi yang diakses per baris tanpa eager loading menimbulkan pola N+1; composer unread count yang dijalankan berulang juga menambah query. Setelah optimasi, masing-masing tercatat 10 dan 9 query.

### 2. Peragakan N+1; matikan `with()` dan tunjukkan lonjakan query di Debugbar.

**Jawaban:** Jalur aman yang sudah dibuktikan otomatis adalah test `PerformanceBudgetTest`: rekap dengan 20 nilai menghasilkan 7 query dan lazy-loading guard aktif di test terkait. Debugbar tidak terpasang, sehingga saya belum dapat menunjukkan panel/screenshot Debugbar. Untuk demonstrasi visual, pasang Debugbar hanya sebagai dependency development di mesin lokal, bandingkan query count dengan dan tanpa `with()`, dan jika perlu nonaktifkan guard hanya di test lokal terisolasi. Jangan pernah mengubah guard atau mengaktifkan Debugbar di production. Panduan langkahnya ada pada bagian “Bagaimana N+1 terjadi dan bagaimana mendemokannya”.

### 3. Apa beda `withCount('students')` dan `count($course->students)`? Kenapa yang kedua boros?

**Jawaban:** `withCount()` meminta database mengembalikan angka jumlah relasi sebagai atribut course; model-model mahasiswa tidak diambil. `count($course->students)` mengakses properti relasi, yang biasanya memuat seluruh mahasiswa menjadi koleksi lalu menghitung di PHP. Di loop course, pola kedua berpotensi mengirim satu query relasi per course dan menghidrasi banyak objek. Jika hanya butuh angka, `withCount()` pada query daftar lebih efisien; `$course->students()->count()` menghindari hidrasi, tetapi pemanggilan berulang tetap bisa menjadi N+1 query count.

### 4. Tunjukkan index yang ditambahkan. Jalankan `EXPLAIN` dan buktikan ia terpakai.

**Jawaban:** Index adalah `assignments(course_id, status, due_at)`, `submissions(user_id, assignment_id)`, dan `grades(graded_at, id)`. Test SQLite menjalankan `EXPLAIN QUERY PLAN`; hasil query tugas menunjukkan `SEARCH assignments USING INDEX assignments_course_status_due_index (course_id=? AND status=? AND due_at>?)`. Itu bukti pemakaian pada SQLite in-memory. Database lokal aplikasi masih melaporkan migrasi Pending; terapkan migrasi dan ulangi `EXPLAIN` di database staging/production agar klaim berlaku untuk server tersebut.

### 5. Sebutkan data aplikasi yang tidak boleh di-cache. Kenapa?

**Jawaban:** Rekap nilai adalah contoh kuat: perubahan nilai perlu segera terlihat, data sensitif, dan hasil bergantung pada authorization course/pengguna. Cache yang basi atau salah scope dapat menampilkan nilai yang tidak semestinya. Notifikasi/unread count juga sengaja tidak dicache agar status baca konsisten setelah aksi pengguna.

### 6. Apa yang terjadi pada `env()` setelah `config:cache`? Kenapa ini penting minggu depan?

**Jawaban:** Setelah config cache dibuat, Laravel tidak memuat `.env` dengan cara normal pada setiap request. `env()` di luar `config/` bisa mengembalikan `null` atau hanya nilai environment proses. Jika kode aplikasi memanggil `env()` langsung, nilai yang tampak benar pada development bisa gagal setelah deployment. Baca konfigurasi runtime memakai `config()`; setelah perubahan environment, clear/bangun ulang config cache dan restart worker yang perlu.

## Pertanyaan kritis tambahan ala dosen

### A. Pengukuran, halaman lambat, dan N+1

**Pertanyaan 1:** Mengapa jumlah query turun 66,2% tidak otomatis membuktikan halaman 66,2% lebih cepat?

**Jawaban:** Query count mengukur banyaknya statement, bukan durasi masing-masing query, waktu PHP, render template, jaringan, lock, atau ukuran payload. Satu query scan besar bisa lebih lambat daripada beberapa query indexed. Untuk klaim latency perlu benchmark waktu respons dengan fixture dan lingkungan konsisten, termasuk persentil dan volume realistis.

**Pertanyaan 2:** Bagaimana membedakan N+1 dari query lambat yang hanya terjadi sekali?

**Jawaban:** Ulangi request dengan jumlah record yang meningkat (misalnya 1, 10, 20) dan catat query per request. Jika jumlah query tumbuh sebanding dengan jumlah baris, curigai N+1; jika query count tetap tetapi satu query mendominasi waktu, periksa SQL dan query plan. `DB::listen`, Debugbar lokal, atau profiler dapat membantu, tetapi gunakan data sensitif secara aman.

### B. Eager loading dan lazy-loading guard

**Pertanyaan 1:** Apakah `with()` selalu lebih cepat daripada query biasa?

**Jawaban:** Tidak selalu. Eager loading mencegah query berulang pada banyak model, tetapi dapat mengambil relasi yang tidak diperlukan atau membuat hasil besar. Muat hanya relasi yang dipakai, batasi kolom jika aman, dan paginasi parent. Ukur query count, data yang dibaca, dan waktu query.

**Pertanyaan 2:** Mengapa lazy-loading guard tidak dinyalakan di production juga?

**Jawaban:** Guard ini dipakai sebagai alat deteksi saat development/testing agar akses relasi terlupa cepat ditemukan tanpa mengubah alur production. Mematikannya di production bukan alasan untuk membiarkan N+1; jalur penting tetap perlu diuji dan dimonitor. Jika aplikasi memilih mengaktifkannya di production, perlu mempertimbangkan dampak exception pada request dan kebijakan error handling.

### C. `withCount()` dan agregasi

**Pertanyaan 1:** Apakah `withCount()` selalu tepat jika view hanya menampilkan jumlah?

**Jawaban:** Biasanya tepat untuk daftar beberapa parent, tetapi query harus memakai nama relasi yang benar dan atributnya (`students_count`) harus digunakan konsisten. Jika parent tunggal atau hitungan dapat dihitung dari data agregat lain, bandingkan query plan. Jangan mengambil koleksi relasi hanya untuk menghitungnya.

**Pertanyaan 2:** Mengapa hasil `withCount()` bisa berbeda dari jumlah yang diharapkan?

**Jawaban:** Scope relasi, soft delete, global scope, filter tambahan, pivot yang duplikat, atau batas tenant dapat memengaruhi baris yang dihitung. Pastikan definisi relasi dan aturan bisnis memang menyatakan himpunan yang ingin dihitung; jangan menganggap count adalah jumlah semua baris mentah.

### D. Index dan `EXPLAIN`

**Pertanyaan 1:** Mengapa urutan kolom dalam index komposit penting?

**Jawaban:** Banyak database mengoptimalkan prefix kiri index. Index `(course_id, status, due_at)` cocok jika query menyaring `course_id` dan `status`, lalu memakai rentang/urutan `due_at`. Query yang hanya menyaring `status` mungkin tidak dapat memanfaatkan prefix secara optimal. Rancang dari pola `WHERE`, join, dan `ORDER BY` nyata.

**Pertanyaan 2:** Jika index ada, mengapa optimizer kadang tidak memilihnya?

**Jawaban:** Untuk tabel kecil, full table scan bisa lebih murah. Statistik yang usang, nilai yang tidak selektif, tipe data/implicit conversion, urutan kolom, atau query berbeda juga dapat membuat index tidak dipilih. Periksa `EXPLAIN` pada database dan data representatif; jangan memaksa index hanya karena namanya ada di schema.

### E. Pagination

**Pertanyaan 1:** Apakah `paginate()` berarti query halaman hanya satu query?

**Jawaban:** Tidak. Laravel dapat menjalankan query hitung total, query data halaman, dan query eager load untuk relasi. Pagination membatasi ukuran hasil utama, bukan menghapus semua query. `simplePaginate()` dapat menghindari total count jika UI tidak memerlukannya; pilih sesuai UX dan kebutuhan.

**Pertanyaan 2:** Apa kekurangan pagination offset pada tabel sangat besar?

**Jawaban:** Halaman offset yang jauh dapat membuat database melewati banyak baris sebelum mengambil halaman berikutnya dan hasil bisa bergeser saat data berubah. Cursor/keyset pagination lebih efisien untuk navigasi berurutan pada tabel besar, tetapi butuh kolom urut yang stabil dan mengubah UX (misalnya tidak langsung ke halaman nomor 100).

### F. Cache dan invalidasi

**Pertanyaan 1:** Apa risiko cache berversi global pada sistem multi-instance?

**Jawaban:** Semua instance harus berbagi backend cache yang sama dan operasi increment harus atomik agar invalidasi terlihat konsisten. Jika tiap instance memakai cache lokal berbeda, satu server dapat terus menyajikan data lama. Uji driver/cache store production, perilaku saat cache unavailable, dan invalidasi pada semua jalur perubahan.

**Pertanyaan 2:** Apakah observer menangkap semua perubahan data?

**Jawaban:** Tidak. Event model menangkap operasi model yang memicu event, tetapi bulk update/delete, SQL langsung, dan perubahan pivot tertentu dapat melewati event model. Itu sebabnya enrollment menginvalidasi cache secara eksplisit, dan perubahan bulk lain yang memengaruhi dashboard juga harus memanggil invalidasi secara eksplisit.

### G. `env()` dan konfigurasi cache

**Pertanyaan 1:** Setelah mengubah `.env`, apakah nilai baru langsung aktif saat `config:cache` sudah pernah dijalankan?

**Jawaban:** Tidak. Konfigurasi cache berisi nilai yang telah dibaca saat cache dibuat. Clear dan bangun ulang cache konfigurasi dalam prosedur deployment, lalu restart worker berumur panjang jika perlu. Jangan membagikan nilai rahasia saat memeriksa konfigurasi.

**Pertanyaan 2:** Mengapa tidak membaca `env()` dari controller agar konfigurasi lebih fleksibel?

**Jawaban:** Karena perilakunya berubah saat config cache aktif dan mengikat kode aplikasi ke mekanisme deployment. File config adalah batas yang membaca environment; bagian aplikasi lainnya membaca API stabil `config()`. Ini juga memudahkan testing dengan mengganti konfigurasi.

### H. Kesiapan deployment dan klaim performa

**Pertanyaan 1:** Apakah hasil test SQLite cukup untuk menyatakan production siap?

**Jawaban:** Belum. SQLite in-memory memastikan perilaku aplikasi/test yang konsisten, tetapi planner, tipe index, konkurensi, volume data, dan cache backend berbeda dari MySQL production. Jalankan migrasi di staging, ulangi `EXPLAIN`, ukur latency dan query dengan data representatif, serta cek log/error setelah deployment.

**Pertanyaan 2:** Apa risiko menjalankan migrasi index pada production?

**Jawaban:** Pembuatan index memerlukan resource dan dapat mengunci/membebani tabel, bergantung database, versi, ukuran, dan opsi online DDL. Jadwalkan deployment sesuai ukuran tabel, backup/rollback plan, cek dukungan online index, dan pantau beban. Test lokal tidak memprediksi durasi migrasi production.
